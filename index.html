Introduction
What is Polymorphism?

The word comes from Greek — poly (many) + morph (form). In programming, it means one interface, many implementations.

Core idea: The same method name can produce different behavior depending on which object it is called on — without the caller needing to know what type that object is.

This is one of the four pillars of OOP alongside Encapsulation, Abstraction, and Inheritance.

🎵
Think of it this way: A music conductor waves the baton and says "play." Every musician responds to that same cue — but a violinist plays strings while a drummer hits the kit. One instruction, completely different execution.
Why does this matter? Without polymorphism, every new type forces you to rewrite existing logic. With it, you extend the system by adding — not modifying.
Core Concepts
Two Types of Polymorphism
Compile Time
Static — Overloading
Same method name, different parameter types or count. The compiler picks the right version before the program runs.
Runtime ← focus here
Dynamic — Overriding
A subclass replaces a parent's method. The correct version is chosen at runtime based on the actual object type.
In practice, when someone says "polymorphism" they mean the dynamic (runtime) variant — it is what makes software truly extensible.
Example · Static
Method Overloading

Same method name, different signatures. The compiler selects the correct version based on what arguments you pass.

Calculator.java
class Calculator { // Two integers int add(int a, int b) { return a + b; } // Three integers int add(int a, int b, int c) { return a + b + c; } // Floating point double add(double a, double b) { return a + b; } } calc.add(2, 3) // → 5 calc.add(1, 2, 3) // → 6 calc.add(1.5, 2.5) // → 4.0

The caller always writes add(). The compiler resolves which implementation to use — no manual branching required.

Example · Dynamic
Method Overriding

A parent class defines a method contract. Each subclass provides its own implementation. The correct one runs at runtime based on the actual object type.

Animal.java
class Animal { String speak() { return "..."; } } class Dog extends Animal { String speak() { return "Woof"; } } class Cat extends Animal { String speak() { return "Meow"; } } // One loop — no type-checking needed Animal[] animals = { new Dog(), new Cat(), new Dog() }; for (Animal a : animals) { System.out.println(a.speak()); } // Output: Woof Meow Woof
Notice the loop does not check what type each animal is. It simply calls speak() and the runtime dispatches to the right method automatically.
Interactive Demo
Shapes and the area() Method

Each shape class overrides area() with its own formula. Toggle shapes on or off — the method call is always identical, only the object changes.

shape.area() — runtime output
The method call never changes:  shape.area()

Adding a new shape — say, Pentagon — requires zero changes to the calling loop. This is runtime polymorphism enabling real-world scalability.

Applications
Where Polymorphism Matters

Polymorphism pays off most when you need to extend a system without modifying existing code — a principle known as the Open/Closed Principle.

🎮
Game Engines
A game loop calls update() and draw() on every entity. Enemies, players, and particles each behave differently — no branching needed.
💳
Payment Systems
payment.process() works for Credit Card, PayPal, or Crypto. New providers integrate without touching the checkout logic.
📄
File Exporters
exporter.export(data) produces PDF, CSV, or Excel. Each format is its own class — the report generator never changes.
🧩
UI Frameworks
Every widget — Button, Input, Modal — extends a base Component with its own render(). The framework renders all of them uniformly.

Key Takeaways

Polymorphism = one interface, many implementations
Static (overloading) is resolved at compile time; dynamic (overriding) at runtime
It enables you to write code against a parent type today that works with any future subtype automatically
The Open/Closed Principle: open for extension, closed for modification
